# AgentForge Benchmark 结果：单 Agent vs 多 Agent 实测对比

> v3（阶段 1 优化后）：2026-10-07 ｜ v2 基线：2026-10-07 ｜ expert 层首测：2026-10-07 ｜ v1 历史数据：2026-09-13（方法有差异，各版数字不可直接比较）｜ 模型：deepseek-v4-flash（temperature=0）

我们给自己的框架出了一道题：**多 Agent 编排到底值不值？** 用框架自带的评测系统（20 个分级任务 × 单/多两种模式 × 每任务 3 次取中位数）实测回答。

> **v3 结论（编排优化后）：多 Agent 19/20（95%），单 Agent 20/20（100%）——成功率与 v2 持平，但多 Agent 编排开销从 +416%/+353% 收窄到 +76%/+51%（耗时/Token），且全部超时清零。编排的开销问题被优化大幅缓解；"何时值得用编排"的边界问题转入 expert 任务集验证。**

> **阶段 2 状态（2026-10-07）**：第四个难度层 expert 已建成并完成首测（ADR-008），任务总数 20 → 25。首测结论：双模式 5/5 打平，多 Agent +327%/+246%，详见"阶段 2：expert 层首测"章节；下方 v2/v3/v1 各版数字均针对原 20 任务。

- easy-03（单Agent）：task timeout after 120s（单次运行超时，多数投票仍通过）

### v2 解读

1. **v1 的"easy 负收益"被部分修正**：v1 中 easy-05 多 Agent 失败是工具不对等所致，修复后 easy 双模式 8/8 打平——但多 Agent 在 easy 上仍付出约 12 倍耗时/9 倍 token，**负收益从"成功率"转移到了"纯成本"**。
2. **hard-04 双模式从全败转全胜**：证实 v1 的失败主要是任务结构性缺陷而非 Agent 能力；hard 层 240s 预算有效。
3. **medium-07 成为唯一失败点，且失败模式变了**：v1 双模式失败是 judge 格式敏感；v2 单 Agent 7.2s 通过（期望值 judge 生效），多 Agent 是 120s 超时 + 155k token——过度拆解在中等任务上依然是编排的软肋，这是阶段 1 优化（复杂度门控）的直接靶点。
4. **多 Agent 抗超时优势消失**：v1 曾观察到"编排拆分后子任务更小、抗超时性更好"，v2 中多 Agent 反而有 3 次超时记录（单 Agent 1 次）——小样本下该结论本就脆弱，如实撤回。

## 阶段 1 优化实测（2026-10-07，v3）

三项编排优化（ADR-007：复杂度门控快速路径 / 审查交接改造 / 判定双通道）与 v2 基线做同日 A/B（两次全量各 20 任务 × 2 模式 × 3 次；单 Agent 为对照臂，两轮 100%、10.5s/11.9s、19.3k/19.0k tokens，波动小，可比）。

### A/B 总体结果

| 指标 | v2 多 Agent | v3 多 Agent（优化后） | 变化 |
|------|------------|---------------------|------|
| 成功率 | 19/20 (95%) | 19/20 (95%) | 持平 |
| 平均耗时 | 54.1s | **20.9s** | **-61%** |
| 平均 Token | 87,337 | **28,712** | **-67%** |
| 与单 Agent 耗时差 | +416% | +76% | 大幅收窄 |
| 与单 Agent Token 差 | +353% | +51% | 大幅收窄 |

单 Agent（对照）：20/20 (100%)，11.9s，18,976 tokens。

### v3 每任务明细（多 Agent 侧关键变化）

| ID | v2 多耗时 | v3 多耗时 | v2 多 Token | v3 多 Token | 备注 |
|-----|----------|----------|------------|------------|------|
| easy-05 | 74.2s | 16.0s | 120,620 | 28,472 | 门控生效 |
| easy-07 | 47.4s | 18.3s | 54,775 | 20,910 | 门控生效 |
| medium-07 | 104.9s（超时） | 27.0s | 155,340 | 39,148 | 不再超时，仍失败（见下） |
| hard-02 | 173.8s | 52.0s | 353,698 | 96,123 | 过度拆解被抑制 |
| hard-03 | 134.1s | **26.4s** | 217,693 | **33,066** | 反超单 Agent（34.0s/66,262） |

（其余任务同向改善或持平；medium-04 多文件操作基本持平——真正的多步任务被判 complex，完整编排保留，符合设计。）

### v3 异常与超时明细

无。v2 的 4 条超时记录全部消失。

### v3 解读（如实）

1. **三项优化中，复杂度门控贡献了绝大部分收益**：easy 多 Agent 耗时 -56%（29.5s→13.1s）、token -59%，"simple 单步免审查"直接砍掉了拆解后的审查与回退开销。
2. **medium-07 失败模式改变，且改变本身有价值**：v2 是"过度拆解 → 审查循环 → 120s 超时 + 155k token"；v3 是"单步快速路径 → Coder 探索烧完 max_turns（8 轮）→ 27s 快速失败"。逐次诊断（手动复现）发现：Coder 在探索中创建测试目录、清理时被 shell 黑名单拦截、反复列目录，轮次耗尽后返回结构化兜底文案。快速路径让这个失败以 1/4 的时间、1/4 的 token 暴露出来——失败得更便宜、更可诊断，但**该任务对当前多 Agent 形态仍是不匹配的**，如实保留失败。
3. **hard-03 上多 Agent 首次反超单 Agent**（26.4s vs 34.0s，33k vs 66k tokens）：需要先设计再实现的任务，拆解带来的结构化反而省了单 Agent 的试错轮次——与"编排价值在更复杂场景"的预期一致，但这是单点观察，不外推。
4. **审查交接与判定双通道的效果无法从成功率单独归因**（v2 基线上 medium/hard 已基本无审查失败样本），其价值在于审查门从"审聊天片段"变为"审磁盘文件"，这属于正确性工程而非指标工程。

**结论：在"单文件、目标明确"的任务集上，优化后多 Agent 的编排开销从 +416%/+353% 降到 +76%/+51%，成功率与单 Agent 保持可比（95% vs 100%）。多 Agent 何时值得用的边界问题，转入阶段 2 的 expert 任务集验证。**

## 阶段 2：expert 层首测（2026-10-07）

第四难度层（5 个任务，绑定 H1 异质角色 / H2 长链条 / H3 上下文规模三假设，ADR-008）的首次实测：5 任务 × 双模式 × 3 次。**难度校准跑先行确认无"伪 expert"**（单 Agent 5/5 通过、耗时 10.5–28.9s、23–84k tokens，与 hard 层同区间）。

### 首测结果

| 指标 | 单 Agent | 多 Agent（四人团队） | 差异 |
|------|---------|---------------------|------|
| 成功率 | **5/5 (100%)** | **5/5 (100%)** | 0 |
| 平均耗时 | 20.7s | 88.3s | **+327%** |
| 平均 Token | 52,229 | 180,533 | **+246%** |
| 超时/错误 | 0 | 0 | — |

| ID | 单耗时 | 多耗时 | 单 Token | 多 Token |
|----|--------|--------|----------|----------|
| expert-01 去重重构 | 23.2s | 116.0s | 51,967 | 223,497 |
| expert-02 规格实现 | 30.2s | 123.0s | 81,423 | 326,703 |
| expert-03 跨文件修 bug | 22.6s | 62.9s | 63,067 | 117,384 |
| expert-04 约定扩展+文档 | 16.8s | 90.7s | 43,345 | 136,584 |
| expert-05 全库盘点 | 10.5s | 48.7s | 21,345 | 98,497 |

### 解读（如实）

1. **三个假设在成功率维度上均未兑现**：即使任务结构上需要异质角色、长链条和跨文件汇总，多 Agent 也没有成功率优势——100% vs 100%。"何时值得用编排"的正收益区间，在当前 25 任务 + deepseek-v4-flash 组合下仍未找到。
2. **开销回归高位的原因清楚**：expert 任务是多阶段计划，复杂度门控不生效（被判 complex，按设计走完整审查），叠加四人团队与长计划上下文携带——+327%/+246% 接近 v2 水平，而全任务集均值（v3 +76%/+51%）是被 easy/medium 的快速路径拉低的。**编排开销与任务复杂度正相关，优化收益集中在简单任务**。
3. **唯一接近打平的 expert-03**（跨文件 bug 修复，1.9x token / 2.8x 耗时）：analyst 的检索定位可能省掉了单 Agent 的试错探索——方向与 H1 预期一致，但样本为 1，不外推。
4. **judge 与 fixture 经受住真实行为**：两模式 10 次运行全判定，判据无误杀无漏判；300s 预算 + 校准跑前固定了超时风险，v2 时代的超时问题未复现。
5. **局限**：单模型（Flash）、5 任务小样本、编排仍是串行执行（DAG/并行未做）——"多 Agent 无用"不是本数据的结论；结论是**在当前形态下编排未见正收益**。若未来换更强模型或引入并行执行，expert 层是现成的重测基准。

## v1 历史数据（2026-09-13，方法学缺陷见上文，数字仅供对照）

> 生成日期：2026-09-13 ｜ 模型：deepseek-v4-flash（temperature=0）｜ 总耗时 71.6 分钟，约 200 万 token

我们给自己的框架出了一道题：**多 Agent 编排到底值不值？** 用框架自带的评测系统（20 个分级任务 × 单/多两种模式 × 每任务 3 次取中位数）实测回答。结论先放这里：

> **在这套任务集上，多 Agent 编排没有带来成功率优势，却付出了约 3.5 倍的 token 成本和 3.7 倍的耗时。** 任务越简单，编排开销越不划算。

## 方法论

- **任务集**：20 个标准任务（8 easy / 8 medium / 4 hard），覆盖文件读写、搜索、代码编写、代码分析、shell 管道等能力
- **两种模式**：单 Agent（全工具 ReAct 循环，max_turns=10）vs 多 Agent（Orchestrator 拆解 → Coder 执行 → Reviewer 审查 → 不通过回退重试）
- **统计方法**：每任务独立运行 3 次，成功率按多数投票（≥2/3），耗时与 token 取中位数；任务级 120 秒超时兜底
- **隔离执行**：每个任务在独立临时目录中运行（线程局部沙箱），互不污染
- **自动评判**：5 种确定性规则评判（contains / file_exists / file_contains / regex / custom），不使用 LLM 评判以保证可复现

### 评测环境本身的修复记录

正式测量前，快速验证跑暴露了评测框架自身的缺陷：**6 个任务引用了"当前项目"中的文件（README.md、agent_forge/ 目录等），但任务在空隔离目录中执行——Agent 无论多正确都必然失败**；另有 1 个任务的自定义评判函数因配置笔误从未生效。全部修复（commit `fbb9c3d`，新增样例项目机制）后才进行本报告的正式测量。修评测环境和修被测系统同样重要——否则测的是坏掉的环境。

## 诚实结论

1. **easy 任务上多 Agent 是明确的负收益**：成功率反而更低（7/8 vs 8/8），耗时约 12 倍、token 约 10 倍。原因直观：简单任务单 Agent 一步到位，而编排路径要额外支付"拆解 + 审查 + 回退"的开销，且这些额外 LLM 调用各自引入新的失败面。
2. **medium/hard 任务上两者打平**：编排没有带来质量提升，但也表现出更好的抗超时性（hard-04 单 Agent 逼近超时边界，多 Agent 拆分后子任务更小——只是 120 秒预算内仍不够）。
3. **多 Agent 的价值区间在别处**：本任务集都是"单文件、目标明确"的任务，本就是单 Agent 的主场。多 Agent 的真实价值应在"需要异质角色并行/长链条依赖/角色隔离上下文"的场景——这不在本任务集覆盖范围内，我们如实标注而不是声称测过。
4. **超时兜底被实测验证**：7 次超时运行全部被正确截断并记录，没有拖垮整轮评测——这正是此前修复的"超时配置从未实现"缺陷的回归验证。

## 局限声明（如实）

- **小样本**：每任务 3 次、共 20 任务；LLM 输出存在非确定性，个别任务的成败在边界波动（如 easy-05 多 Agent 3 次中 2 次失败即判失败）
- **规则评判的格式敏感性**：medium-07（shell 管道统计行数）双模式均失败——judge 正则 `\d+\s+\S+\.py` 对输出格式敏感，Agent 可能算对了但表述格式不匹配。规则 judge 的宽严权衡是评测系统设计的固有难题
- **单一模型**：全部结论基于 deepseek-v4-flash，未跨模型验证
- **hard-04 双模式失败**：最重的任务（全目录统计分析 + 写报告）超出 120 秒预算，说明超时预算需要按任务难度分级
- **温度 0 不等于可复现**：LLM 服务端仍有非确定性，绝对数字会有波动，趋势（成本差异、easy 上的负收益）比单点数字更可信
