# ADR-006：Benchmark 测量有效性修复

> **状态**：已采纳
> **日期**：2026-10-07
> **决策者**：宇诚
> **影响范围**：benchmark 评测方法、Specialist 工具配置
> **触发**：2026-09-13 全量实测（docs/benchmark-results.md）的事后复审

---

## 背景

2026-09-13 的全量实测（20 任务 × 单/多模式 × 3 次）得出"单 Agent 90% vs 多 Agent 85%，后者成本 3.5 倍"的结论。事后复审发现该测量本身存在四个有效性问题——不修复它们，数字就不是对"编排范式"的公平测量：

1. **hard-04 结构性缺陷漏修**：任务描述要求"分析 agent_forge/ 目录"，但 `fbb9c3d` 修复 6 个同类任务时漏掉了它——它在空隔离目录中执行，双模式均超时失败（120s），失败原因很可能是任务坏了而非 Agent 不行。
2. **两种模式工具不对等**：单 Agent 模式用 `ALL_TOOLS`（含 grep_search），多 Agent 模式的 CoderAgent 硬编码列表缺 grep_search——且 registry 路径（`bind_tools(EXECUTE)`）本就返回全部 4 件，两条构造路径不一致。easy-05（文件搜索）多 Agent 失败，混入了工具配置差异。
3. **medium-07 judge 格式敏感**：regex `\d+\s+\S+\.py` 匹配 agent_output，Agent 可能算对但表述为 `base.py: 7` 即被判失败（局限声明已如实记录，双模式均"失败"）。
4. **错误信息断链**：runner 采集、aggregate_runs 保留的 errors（超时/judge 异常/setup 失败）从未被 Reporter 渲染——easy-05 失败原因、6 个任务的超时只能靠"耗时恰好 120.0s"反推，进程结束诊断信息即丢失。

---

## 决策 1：hard-04 补 setup + hard 层超时分级 240s

### 备选方案

**方案 A：只修 hard-04 的 setup，超时维持全局 120s**
- 最小改动，但 hard-04 是最重的任务，120s 预算下仍可能结构性超时

**方案 B：hard 层 4 个任务统一 `timeout: 240`（我们的选择）**
- `TaskDefinition` 本就支持任务级 timeout 覆盖，只是从没有任务用过
- 与 2026-09-13 报告局限声明的判断一致（"超时预算需要按任务难度分级"）

**方案 C：全部任务统一放宽到 240s**
- easy/medium 拉长无意义任务的失败等待，且改变大多数任务已验证的测量条件

### 决定

选择方案 B。hard-04 setup 复用 `sample_project.create()` 机制（与 easy-05 等任务一致）。

### 风险

整轮实测耗时上升（最坏 +48 分钟），换取 hard 层任务的真实成功率。

---

## 决策 2：Specialist 两条构造路径对齐（工具对等）

### 备选方案

**方案 A：给 CoderAgent/ReviewerAgent 硬编码列表补 grep_search（我们的选择）**
- registry 路径 `bind_tools(EXECUTE/READ)` 本就返回含 grep 的工具集，硬编码路径是漏了而非设计差异
- grep_search 是 READ 级工具，"资深工程师"和"审查专家"拥有它符合角色设定

**方案 B：给单 Agent 模式限制工具集**
- 为对齐而削弱"全能工程师"的基线能力，方向反了

**方案 C：保持不对等，仅在文档声明**
- 测量继续混淆"编排能力"与"工具配置"两个变量

### 决定

选择方案 A。`test_registry.py` 的默认工具集断言从仅 Writer 扩展到 Coder/Reviewer，固化"硬编码 == registry 过滤结果"的对称约束。

### 风险

demos 中默认构造的 Coder/Reviewer 行为变化（多一个只读搜索工具，良性）。**新旧实测数字不可直接比较**——这是本轮修复的目的本身。

---

## 决策 3：medium-07 改期望值 custom judge

### 备选方案

**方案 A：放宽 regex（如忽略空白差异）**
- 仍是格式匹配，只是换一种格式敏感

**方案 B：改任务为"写入文件 + file_contains 评判"**
- 需要改任务描述本身，改变被测任务

**方案 C：custom judge 从工作目录重算 ground truth（我们的选择）**
- setup 创建的样例项目行数已知，judge 时重新计算 top-5 作为期望值
- 输出中"文件名与行数同行出现"即认，兼容 `7 base.py` / `base.py: 7` / `base.py（7 行）` 等表述
- 数字匹配加 `(?<!\d)/(?!\d)` 防 7 误配 17；行数口径同时接受 splitlines 与 wc -l 两种约定

### 决定

选择方案 C。评判从"匹配格式"升级为"验证答案"。

### 风险

judge 过严会错杀正确 Agent——用多格式单测先行压住；实测中若仍误杀再放宽。

---

## 决策 4：报告渲染异常与超时明细

### 备选方案

**方案 A：维持现状（errors 到聚合层为止）**
- 报告干净，但诊断信息随进程结束丢失

**方案 B：Reporter 新增"异常与超时明细"节（我们的选择）**
- 按任务×模式列去重 errors，每条截断 200 字符；无错误时不输出本节

**方案 C：运行级数据持久化为 JSON/CSV**
- 更彻底，但属于新功能，本轮以最小改动补断链

### 决定

选择方案 B。方案 C（运行级数据持久化）留给后续迭代。

### 风险

错误较多的报告会变长——可接受，这正是明细存在的意义。
