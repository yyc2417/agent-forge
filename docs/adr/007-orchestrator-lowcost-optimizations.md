# ADR-007：Orchestrator 低成本优化

> **状态**：已采纳
> **日期**：2026-10-07
> **决策者**：宇诚
> **影响范围**：AgentForge 多 Agent 编排架构
> **触发**：2026-10-07 v2 基线实测（成功率 95% vs 100% 打平，但多 Agent 成本 4.5 倍 token / 5.1 倍耗时；唯一失败点 medium-07 为过度拆解超时）

---

## 背景

v2 基线（ADR-006 修复测量方法后）显示：单/多 Agent 成功率接近打平，多 Agent 的开销集中在三处——

1. **拆解无门控**：任何任务都走完整"拆解→执行→审查（→回退）"流程。easy 任务上约 12 倍耗时是纯编排开销；medium-07（中等任务）过度拆解直接导致 120s 超时失败。
2. **审查交接失真**：`_call_reviewer` 把任务截到 200 字符、Coder 产出截到 2000 字符传给 Reviewer，Reviewer 不知道 Coder 写了哪个文件——审查门审的是"聊天记录片段"而非真实产物。
3. **判定格式脆弱**：Reviewer 靠输出中精确出现【通过】/【不通过】标记，LLM 漏写标记即保守判不通过，触发回退重跑（token/超时放大器）。

---

## 决策 1：复杂度门控快速路径

### 备选方案

**方案 A：拆解 LLM 自判复杂度（我们的选择）**
- 拆解 prompt 的 JSON 契约新增 `"complexity": "simple"|"complex"`；simple 且恰好 1 步 → 跳过审查门
- 零额外 LLM 调用（复杂度判定随拆解顺带产出）

**方案 B：启发式规则门控（任务长度/关键词）**
- 零 LLM 成本，但"一步可完成"无法用规则可靠判定，误判率高

**方案 C：独立路由节点先分类再拆解**
- 多一次 LLM 调用，把 easy 任务的编排开销从"1 次拆解"变成"1 次分类 + 1 次拆解"，与优化目标背道而驰

### 决定

选择方案 A。保守语义三重防线：

- complexity 缺失 / 非法 JSON / 非 simple 值 → 按 complex 走完整审查
- 标 simple 但计划多步 → 仍走完整审查（多步产出的组合质量必须把关）
- 拆解 LLM 异常走 fallback 计划 → 按 complex

### 风险

LLM 把需要质量把关的任务误标 simple → 审查被跳过。缓解：prompt 中明确"不要把需要质量把关的任务标为 simple"；误标代价 = 少一次审查，不是不可逆破坏。

---

## 决策 2：审查交接读真实文件

### 备选方案

**方案 A：继续传截断文本（现状）**
- Reviewer 无从核对磁盘内容，审查门形同虚设

**方案 B：传截断文本 + 文件路径列表（我们的选择）**
- 完整任务（上限 500）+ 产出上限 8000 + 从产出提取文件路径（去重保序，上限 8 个）
- prompt 明确要求"用 read_file 实际读取，磁盘文件是唯一事实源"

**方案 C：在框架层记录 Coder 的 write_file 调用轨迹，结构化交接**
- 最精确，但需要在 BaseAgent/tool 层加写入追踪，改动面大；留作后续迭代

### 决定

选择方案 B。Reviewer 的 max_turns=3 够用（一轮可批量读取，剩余轮次判定）。

### 风险

审查调用 token 上升（产出上限从 2000 到 8000）——但审查只在 complex 任务上运行（决策 1 已把 simple 任务摘出），且换来的是审查门真正有效。

---

## 决策 3：判定双通道（JSON 优先，标记兜底）

### 备选方案

**方案 A：维持纯标记匹配**
- 语义脆弱，漏写标记 → 意外回退重跑

**方案 B：纯 JSON 判定**
- 契约干净，但旧格式输出（含既有测试与真实运行中的标记文本）全部失效，兼容性断崖

**方案 C：双通道（我们的选择）**
- prompt 要求首行输出 `{"verdict": "pass"|"fail"}`；解析先走 JSON 提取（扫描所有最小 JSON 对象，取第一个含合法 verdict 的）
- JSON 缺失/非法 → 回退【通过】/【不通过】标记精确匹配，保守方向不变（无信号 = 不通过）
- JSON 与标记同时出现且矛盾 → JSON 优先（ instructed 契约）

### 决定

选择方案 C。判定从"匹配措辞"升级为"读取结构化字段"。

### 风险

JSON 提取可能匹配到审查正文中的无关 JSON 片段——限定"第一个含合法 verdict 的对象"，正文引用 `{"verdict": ...}` 讨论的场景极为罕见。

---

## 效果验证

三项优化以独立提交交付（复杂度门控 / 交接改造 / 判定双通道），对 v2 基线做全量 A/B 重跑，逐任务对比。若某项无效果或负效果，按提交粒度回退。实测数据见 docs/benchmark-results.md 对应章节。
